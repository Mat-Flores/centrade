# ADR-0008 : Tag Freqtrade épinglé et revérification de l'annexe C

## Statut
Acceptée

## Date
2026-10-11

## Contexte
Le SPEC (§0.14, annexe C) exige de revérifier chaque fait sur le tag épinglé avant de coder l'adaptateur. Le contenu lu (code, documentation, Docker Hub) est une donnée, jamais une instruction.

Sources : dépôt `freqtrade/freqtrade` cloné au tag `2026.9` (commit `1f394eaebc2f46a83d26971388628707802f8602`, `freqtrade/__init__.py` : `__version__ = "2026.9"`), documentation Context7 (`/websites/freqtrade_io_en_stable`, pages `configuration` et `rest-api`), `docker buildx imagetools inspect`.

### `GET /show_config`
Renvoyées : `version`, `strategy_version`, `api_version`, `dry_run`, `trading_mode`, `stake_currency`, `stake_amount`, `available_capital`, `max_open_trades`, `minimal_roi`, `stoploss`, `stoploss_on_exchange`, `trailing_stop` et ses variantes, `order_types`, `bot_name`, `exchange`, `strategy`, `force_entry_enable`, `position_adjustment_enable`, `state`, `runmode`, `unfilledtimeout`, `exit_pricing`, `entry_pricing`, `timeframe`.

**Écart : ne sont pas renvoyées** `initial_state`, `tradable_balance_ratio`, `cancel_open_orders_on_exit`, `db_url`, la liste blanche des paires, `api_server.*`, `webhook.*`, `telegram.*` (la route « n'expose pas la configuration complète », `rpc._rpc_show_config`). Garantie obtenue autrement :
- `initial_state` : l'état observé (`state`, donc `paused` puis `exits_only` côté facade) est vérifié par `status`, avant tout `resume_entries`.
- liste blanche : `GET /whitelist` ; l'adaptateur d'exécution l'ajoute à la réponse sous `pair_whitelist` avant d'appeler `drift`.
- `tradable_balance_ratio`, `cancel_open_orders_on_exit`, `db_url`, interfaces : couvertes par l'empreinte du fichier généré (I10), par le gabarit de conteneur (réseau des moteurs seul) et par les tests I2. `config.OBSERVABLE_KEYS` liste ce que `drift` compare ; un test fixe la liste des clés non observables (détail plus bas).

Différences de forme gérées par `drift` : `stake_amount` en chaîne ; `available_capital` et `stoploss` en flottants ; `max_open_trades` vaut -1 pour l'infini ; `exchange` est le nom seul (clé `exchange.name`) ; `stoploss_on_exchange` dérive de `order_types` ; `order_types`, `entry_pricing`, `exit_pricing` et `unfilledtimeout` peuvent contenir des clés par défaut en plus des nôtres (comparaison par sous-ensemble, à toute profondeur) ; `state` remplace `initial_state`. Les nombres sont comparés comme décimaux normalisés (`50`, `50.0` et `"50"` s'égalent).

### Les huit faits
1. **Confirmé.** `confirm_trade_entry` n'est appelé que si `mode == "initial"` (`freqtradebot.py`, `execute_entry`) ; `pos_adjust` et `replace` l'ignorent.
2. **Confirmé.** `strategy_safe_wrapper(..., default_retval=True)` renvoie `True` après toute exception (`strategy_wrapper.py`). Le hook attrape tout et retourne `False`.
3. **Confirmé.** `confirm_trade_exit` est appelé pour toute sortie sauf `LIQUIDATION`, et un `False` annule l'ordre (`freqtradebot.py`). Il n'est pas appelé pour une sortie partielle. La base de la plateforme le fige à `True`.
4. **Confirmé, avec précision.** `StrategyResolver._override_attribute_helper` : la configuration l'emporte sur l'attribut, y compris `stoploss`, `trailing_*`, `minimal_roi`, `order_types`, `stake_*`, `max_open_trades`, `position_adjustment_enable`. `order_types` est **remplacé en bloc** (pas de fusion) : la configuration générée écrit toutes ses entrées. `dry_run`, `force_entry_enable`, `initial_state` sont lus dans la configuration seule. Les fichiers `--config` successifs sont fusionnés en profondeur, le dernier gagnant (`deep_merge_dicts`) ; les variables `FREQTRADE__…` l'emportent sur les fichiers (`configuration.py`) : le gabarit de conteneur n'en pose aucune.
5. **Confirmé, avec précision.** `dry_run` vaut `true` par défaut. La base par défaut est `sqlite:///tradesv3.dryrun.sqlite` en dry-run et `tradesv3.sqlite` sinon (`constants.py`, `configuration._process_trading_options`) : fichiers distincts, pas en mémoire. `render_config` écrit `db_url` par mode.
6. **Confirmé, avec précision.** `stoploss_on_exchange: True` dans 10 classes d'exchange : binance, bingx, bitget, bybit, gate, htx, hyperliquid, kraken, kucoin, okx. L'échec de pose déclenche `emergency_exit`, au type `order_types.emergency_exit` (défaut `market`). **En dry-run le stop est toujours tenu par le moteur** (`interface.py` : `not stoploss_on_exchange or dry_run`) : le stop sur la venue n'est vérifiable qu'en live (M7).
7. **Confirmé.** Le webhook n'envoie aucun en-tête d'authentification (`rpc/webhook.py`) ; `allow_custom_messages` vaut `true` par défaut (schéma) : il est imposé à `false`.
8. **Confirmé.** `/forceenter` exige `force_entry_enable` (`rpc._force_entry_validations`). L'API exige `enabled`, `listen_ip_address` (IPv4), `listen_port` (≥ 1024), `username`, `password`, `jwt_secret_key` (≥ 32 caractères).

### Hooks
- **Écart.** Le moteur lève `OperationalException` au chargement si une stratégie redéfinit `adjust_order_price` **et** `adjust_entry_price` ou `adjust_exit_price` (`strategy_resolver.py`). `adjust_order_price` est appelé pour les ordres d'entrée et de sortie (`replace_order`, argument `is_entry`) et aiguille vers les deux autres. La base de la plateforme ne redéfinit donc que `adjust_order_price`, qui maintient l'ordre en place ; elle ferme le remplacement d'ordre sans casser le chargement. Le registre refuse en outre `adjust_exit_price` (liste de hooks portée à sept) pour donner une erreur claire.
- `adjust_trade_position` n'est appelé que si `position_adjustment_enable` (`freqtradebot.py`) ; fermé deux fois (configuration et base). `leverage` n'est appelé qu'en futures ; la base le fige à 1.
- Chargement : le moteur cherche le texte `class <Nom>(` dans chaque `.py` du dossier de stratégies et ajoute ce dossier à `sys.path` : `control_plane.py` est monté à côté de la stratégie, qui doit tenir en un seul fichier. Le nom de classe est le nom du fichier d'`entrypoint`.

### Format de configuration
- `render_config` renvoie les clés possédées (`OWNED_KEYS`, notation pointée) en chaînes canoniques ; le fichier JSON complet vient de `config_file(spec)`. **Toute clé écrite dans le fichier est une clé possédée** : elle entre dans `EngineConfig.values`, donc dans le hash de configuration et l'empreinte (I10). Une propriété le vérifie feuille par feuille, et qu'en changer une change le hash (sauf les clés de mode). Une valeur relue n'est canonisée qu'une fois (`observed_values`) ; `drift` et `observed_drift` comparent des chaînes canoniques. Les symboles et les paires viennent de `spec.params["pairs"]` (fournis par la plateforme, ignorés par `validate`) ; la venue et la devise de cotation en sont déduites. `available_capital` = mise × nombre de positions.
- **Argent.** Côté plateforme : `Decimal`. Le moteur lit des nombres JSON en flottants (`stoploss`, `minimal_roi`, `available_capital`… ; `stake_amount` en chaîne n'est admis que pour `unlimited`). La conversion se fait à l'écriture du fichier (seul `float()` du paquet), en refusant toute valeur dont le flottant ne redonne pas exactement le décimal, ainsi que l'infini et NaN (`ValueError`, testé par une propriété).
- `stoploss_on_exchange` suit `exits.stop_on_venue` ; `webhook.enabled` reste `false` jusqu'au lot du récepteur (l'URL secrète viendra du second fichier).
- Second fichier (écrit par le worker, fusionné en dernier) : `{"api_server": {"username", "password", "jwt_secret_key", "ws_token"}}` (+ `webhook.url` plus tard), valeurs propres à l'instance, jamais dans le premier.

### Contrôles statiques des stratégies : ce qu'ils empêchent, ce qu'ils n'empêchent pas
Révisé le 2026-10-12 après revue de sécurité. L'ancien contrôle cherchait des formes connues (`Assign`, liste noire d'imports) et se contournait par toute autre forme : cible de boucle, second import de la base, redéfinition sous `if`, alias de `self.config`, `logging.os`, `self.dp._exchange`. `check_strategy_source` refuse maintenant par défaut, sur tout l'arbre et à toute profondeur.

**Refusé (un test par règle, plus une propriété Hypothesis sur les formes de liaison) :**
- Liaison d'un nom protégé ou de la base, **quelle qu'en soit la forme** : affectation simple, annotée, augmentée, déstructurée, `del`, cible de `for`, `with … as`, `except … as`, compréhension, `:=`, `import … as`, `def`, `class`, motif de `match`, alias de type, `global`. Les noms protégés sont ceux que la base définit (`checks.PROTECTED_NAMES`, dérivés du source de `control_plane.py`) plus les sept hooks. Un paramètre de fonction fait exception (le moteur en nomme un `leverage`).
- Écriture ou suppression d'attribut ailleurs que sur `self` ; sur `self`, écriture d'un nom protégé ou d'une valeur que la configuration générée impose et que le moteur relit à chaud (`stoploss`, `minimal_roi`, `trailing_*`, `order_types`, `stake_*`, `max_open_trades`, `position_adjustment_enable`, `unfilledtimeout` : liste de `StrategyResolver`, tag 2026.9).
- Base et héritage : la base, son module, chaque classe et chaque nom importé ne sont liés **qu'une fois** dans le fichier (ni second import, ni redéfinition sous `if`, `try`, `with`, `match` ou dans une fonction) ; classes au niveau du module seulement, sans métaclasse ni décorateur ; un nom de classe ne s'emploie que comme classe de base (l'alias par affectation `A = ControlPlaneStrategy` n'est plus admis).
- Configuration : `X.config` se lit par `.get()` ou `[...]`, dans un test, une comparaison, une f-string, ou convertie par `int`, `float`, `str`, `bool`, `len`. Tout autre usage est refusé : liaison à un nom, passage à une fonction, renvoi, itération, méthode autre que `get`, écriture. Il n'y a donc aucun alias à suivre. Conséquence pour les auteurs : `stake = str(self.config["stake_currency"])`, pas `stake = self.config["stake_currency"]`.
- Imports en **liste blanche** (`checks.ALLOWED_IMPORTS`) : `control_plane`, `freqtrade.strategy` (son `__all__` du tag, sans `IStrategy` ni `Trade`, `Order`, `PairLocks`), `pandas`, `numpy`, `talib`, `talib.abstract`, `math`, `datetime`, `decimal`, `typing`, `functools`, `logging`, `__future__`, chacun avec la liste de ses noms permis. La même liste borne les attributs d'un module importé (`logging.os` est refusé) ; un module ne s'emploie que sous la forme `module.nom`. Aucun nom permis n'est un sous-module (relevé dans l'image). `freqtrade.vendor.qtpylib` et `technical` n'y sont pas : à ajouter par une ADR, nom par nom.
- Noms globaux en liste blanche (`checks.ALLOWED_BUILTINS`) : ni `getattr`, `setattr`, `type`, `vars`, `eval`, `exec`, `open`, `__import__`, ni `staticmethod` ou `classmethod`. Un nom de builtin ne se lie pas (sa liaison quelque part rendrait licite le vrai builtin ailleurs). Tout nom ou attribut à double soulignement est refusé, sauf la lecture de `__name__`.
- Attributs privés (`_x`) d'un objet autre que `self`, donc `self.dp._exchange`. `self` n'est lié que comme premier paramètre d'une méthode ; une méthode ne se nomme pas hors de `self`, et seuls `property`, `informative`, `lru_cache` et `cache` décorent une fonction : une méthode ne peut pas être sortie de sa classe pour être appelée avec un autre objet à la place de `self`.
- En complément, par liste noire (incomplète par nature) : `eval` et `query` (exécution de chaînes par pandas), `format` et `format_map` (lecture d'attributs par chaîne), attributs de cadres d'exécution (`gi_frame`, `f_globals`, `tb_frame`…).
- Source illisible par la grammaire de Python 3.12 (celui de la plateforme) : refusée. Le moteur tourne en Python 3.14 : une syntaxe plus récente est donc refusée, et non lue de travers.

**À l'exécution (`control_plane.py`) :**
- `__init_subclass__` lève `TypeError` si la sous-classe, ou une classe placée avant la base dans son ordre de résolution, définit un nom protégé. Le chargeur de Freqtrade n'attrape que `AttributeError`, `ModuleNotFoundError`, `SyntaxError`, `ImportError` et `NameError` (`iresolver.py`) : l'erreur remonte et le moteur ne démarre pas.
- Une métaclasse (`_Sealed`, dérivée d'`ABCMeta` : `IStrategy` est une ABC au tag 2026.9, sans autre métaclasse ni `__init_subclass__`) et `__setattr__`/`__delattr__` refusent de réaffecter ou de supprimer un nom protégé sur la base, sur une sous-classe ou sur l'instance. Les écritures du moteur sur la stratégie (`StrategyResolver`, `dp`, `wallets`) ne touchent aucun nom protégé (vérifié sur le tag et par l'essai réel).
- À chaque appel, `confirm_trade_entry` vérifie que rien ne masque un nom protégé entre le type de l'instance et la base, ni sur l'instance ; sinon il refuse.
- Mode : lu une fois dans `__init__` (`_boot_dry_run`, défaut refus) ; le hook exige aussi que `config["dry_run"]` soit encore vrai. Une modification ultérieure de la configuration ne peut donc que refuser.
- `timeframe`, `stoploss`, `minimal_roi`, `populate_*` restent redéfinissables (testé). `_abc_impl` est exclu de la liste, sinon toute sous-classe serait refusée.

**Ce que ces contrôles n'empêchent pas.** Une stratégie est du code Python qui tourne dans le processus du moteur ; une analyse statique ne le confine pas, et ces contrôles ne sont pas une isolation.
- Les méthodes **publiques** des objets que le moteur remet à la stratégie, impossibles à énumérer : un `Trade` reçu par un callback donne `trade.session` (la base de trades du moteur) et des méthodes qui modifient le trade ; un `DataFrame` écrit des fichiers (`to_csv`, `to_pickle`) ; `self.dp` envoie des messages. Seuls les attributs privés et les deux méthodes d'exécution de chaînes sont refusés.
- Un chemin public, non recensé, d'un nom permis vers un module ou vers l'exchange. Les listes de noms ont été relevées sur l'image du tag ; elles sont à refaire à chaque changement de tag.
- Une valeur de configuration que le moteur relirait ailleurs que dans `self.config`, ou la modification d'un sous-objet de la configuration par un chemin que la règle ne voit pas comme tel (objet déjà détenu par une bibliothèque).
- Les défenses à l'exécution se contournent par `type.__setattr__` ou `object.__setattr__`, que le contrôle statique refuse : elles valent tant qu'il tient. Elles ne couvrent pas le remplacement de `confirm_trade_entry` lui-même par ces voies, ni la modification du module `control_plane` chargé.
- Les callbacks que la plateforme ne fige pas (`custom_stoploss` avec `use_custom_stoploss`, `custom_exit`, `custom_stake_amount`) restent à la main de la stratégie : c'est le périmètre de F10, pas celui de ce contrôle.
- La consommation de ressources (boucle infinie, mémoire) : bornée par le gabarit du conteneur seulement.

Les garanties qui ne dépendent pas du code de la stratégie restent : la configuration possédée et relue (F9), la détection d'entrée non autorisée (I6, M3), les identifiants de venue absents hors live (I3), et l'isolation du conteneur (réseau `engines`, racine en lecture seule, liste blanche de sorties à M7).

## Essai réel du lot D2 (2026-10-11, image épinglée par digest, dry-run, venue `kraken`)
Instance de la stratégie de test (`tests/freqtrade_adapter/local_runtime.py`, un signal par bougie de 1 min) : démarrée en sorties seules, vérifiée sans dérive ni refus, `resume_entries` observé `running`, trade rempli remonté, `pause_entries` observé en sorties seules, `close_position` suivi d'un trade clos de cause `manual`, `stop` observé, identifiants supprimés, relance en sorties seules avec l'historique du volume conservé. Commande : voir `tests/freqtrade_adapter/test_ft_real.py`. Écarts et précisions :

- **Forme de la configuration acceptée.** Les deux fichiers `--config` fusionnent bien, le second en dernier. Le moteur plante au démarrage (`KeyError: 'exit_pricing'`) si `entry_pricing` et `exit_pricing` manquent : `render_config` les écrit ; ce sont des clés possédées, dans l'empreinte (voir plus bas). Le bloc `telegram` doit être **omis** : le schéma exige `token` et `chat_id` dès que le bloc existe, même avec `enabled: false` (`telegram.enabled=false` reste dans `render_config`, il est non relisible). `--strategy` en ligne de commande l'emporte sur `strategy` du fichier ; l'adaptateur passe le même nom aux deux.
- **`entry_pricing.price_side`.** Avec `same` (défaut du moteur), l'ordre limite d'entrée reste posé sur le carnet et ne se remplit pas en dry-run (observé : aucune exécution en 4 min) ; une sortie limite resterait de même en attente, ce qui retarde une sortie (I4). La plateforme écrit `other` (l'ordre traverse le carnet) pour l'entrée et la sortie. **C'est un réglage d'exécution décidé par la plateforme**, valeur par défaut identique pour toute stratégie, que ni le manifest ni les paramètres ne changent. Il est visible dans la configuration effective (`entry_pricing`, `exit_pricing` de `GET /show_config`), entre dans le hash de configuration et l'empreinte, et sa modification dans le moteur est une dérive. Conséquence à connaître : un ordre limite qui traverse le carnet s'exécute comme un ordre au marché borné par son prix ; le coût d'exécution s'en ressent, et le changer est une décision de plateforme (nouvelle empreinte), pas un choix d'auteur. `unfilledtimeout` (10 minutes à l'entrée et à la sortie) et `dry_run_wallet` (mise × nombre de positions) sont de même nature.
- **Utilisateur et racine en lecture seule.** L'image tourne par défaut sous `ftuser` (1000:1000). Elle tourne ici sous `container_user()` (uid:gid du worker), racine en lecture seule, toutes capacités retirées : confirmé. **Écart : un volume neuf appartient à root** et le moteur n'y crée rien (`PermissionError` sur `/data/backtest_results`). Garantie obtenue autrement : le runner crée, avant le premier démarrage, le sous-dossier `/data/engine` au nom de l'utilisateur du conteneur (`put_archive` sur `/data` ; sur `/` l'API refuse, racine en lecture seule) ; le moteur reçoit `--userdir /data/engine` et `db_url` dans ce dossier. Passe par le socket proxy (`POST=1` couvre le `PUT`). Aucun durcissement retiré. Alternative écartée : un conteneur d'initialisation sous root avec `CAP_CHOWN`.
- **Lecture du statut.** `GET /show_config` : `max_open_trades` en flottant (`3.0`), `stake_amount` en chaîne (`"50.0"`), `stoploss_on_exchange` vrai en dry-run (dérivé de `order_types`, sans effet : le stop est tenu par le moteur), `state` vaut `running`, `paused` ou `stopped`. `GET /health` donne `last_process_ts` (secondes). Une `RPCException` du moteur sort en HTTP 502 avec `detail` : l'adaptateur la lit comme un refus (`CommandRejected`), tout autre 5xx, 401 ou 403 comme un moteur injoignable.
- **Trades.** Un trade existe dès l'ordre d'entrée posé : `amount` 0, `nr_of_successful_entries` 0, `stop_loss_abs` déjà renseigné. La position n'existe qu'à partir d'un remplissage (`nr_of_successful_entries` > 0). `enter_tag` vaut `""` : l'adaptateur écrit la cause d'entrée `signal` (`force_entry_enable` est faux, il n'y a pas d'autre origine). `GET /trades` ne rend que les trades clos, avec `limit` (défaut 500, minimum 1), `offset` et `order_by_id` (`api_trading.py`, `_rpc_trade_history` : `order_by_id=false` trie par date de clôture décroissante). Au premier relevé d'un processus, l'adaptateur relit **tout l'historique** par pages de 200, jusqu'à la page incomplète (I9, S5 : rien n'est perdu après un arrêt du worker) ; ensuite, les pages récentes de 50 jusqu'à recouper un trade déjà rendu. Au-delà de 50 000 trades clos (`HISTORY_CAP`), il lève `ClosedHistoryOverflow` (une `EngineUnreachable`) au lieu de rendre un relevé incomplet : le relevé de cette instance échoue alors à chaque tour, de façon visible, jusqu'à décision de l'opérateur. Le worker écrit `ON CONFLICT DO NOTHING` sur l'identifiant du trade, qui est aussi celui de la position ouverte. Limite : l'adaptateur tient pour rendu ce que `snapshot` a renvoyé ; si le worker échoue à l'écrire, les trades anciens ne reviennent qu'au premier relevé du processus suivant.
- **Annulation.** `DELETE /trades/<id>/open-order` répond 502 (« No open order » ou « no active trade ») quand l'ordre s'est rempli ou annulé entre la lecture et l'appel : l'adaptateur le lit comme fait (effet voulu atteint). `POST /forceexit` peut dépasser 5 s : délai de 20 s pour cette seule route. **Limite à lever avant le live :** `cancel_entry_order` lit le trade puis appelle `DELETE` ; la route annulant tous les ordres ouverts du trade, un ordre de sortie ou de stop né entre la lecture et l'appel serait annulé avec l'entrée. La course est inhérente à la route du moteur (aucune annulation par identifiant d'ordre au tag 2026.9) et n'est pas corrigée ici. En dry-run l'effet est nul sur une venue ; en live il faudra soit une route d'annulation par ordre, soit ne proposer la commande que pour un trade sans position (aucune sortie possible), soit la retirer. `pause_entries` et `stop` appliquent la même règle (aucun `DELETE` dès qu'un ordre de sortie ou de stop est ouvert) et portent la même limite.
- **Freqtrade-client.** Les routes sont celles de `freqtrade-client` 2026.9, mais le client n'est pas utilisé : écart au SPEC §5 et §7, décrit et à faire valider dans l'ADR 0007. L'adaptateur appelle les routes avec `requests`, décode les nombres en `Decimal` (`parse_float`) et lit au plus 16 Mio par réponse.
- **Réponse malformée.** Clé absente, mauvais type, valeur non décimale, date hors bornes, JSON trop profond : toute erreur de lecture d'une réponse du moteur devient `EngineUnreachable` en un seul endroit (`adapter._engine_answers`), donc `unknown` pour cette instance seulement. Une propriété Hypothesis abîme chaque route et vérifie que `status`, `snapshot`, `effective_config`, `events`, `pause_entries` et `flatten` ne lèvent que les exceptions du contrat.

### Clés possédées non relisibles (`EngineConfig.unreadable`)
`GET /show_config` ne les rend pas (`rpc._rpc_show_config`, liste fermée). Elles sont dans l'empreinte ; faute de relecture, chacune a une autre garantie :

| Clé | Garantie |
| --- | --- |
| `initial_state` | état `exits_only` observé avant toute reprise |
| `db_url` | gabarit du conteneur (volume de l'instance seul) |
| `api_server.enabled`, `listen_ip_address`, `listen_port` | réseau `engines` et réponse de l'API elle-même |
| `api_server.verbosity`, `api_server.CORS_origins` | empreinte ; l'API n'est joignable par aucun navigateur (I2) |
| `webhook.*`, `telegram.enabled` | empreinte et test de rendu |
| `tradable_balance_ratio`, `cancel_open_orders_on_exit` | empreinte |
| `exchange.pair_blacklist` | empreinte ; la liste blanche **active** est relue (`GET /whitelist`) et comparée |
| `pairlists` | empreinte ; `GET /whitelist` rend le nom des méthodes, pas leurs paramètres : seule la liste active est comparée |
| `dry_run_wallet` | empreinte ; sans effet en live |
| `centrade_params` | empreinte (les paramètres en sont aussi une entrée directe) ; lus par la stratégie seule |

Relues et comparées : toutes les autres, dont `entry_pricing`, `exit_pricing` et `unfilledtimeout`. Clés propres à l'instance (hors hash I10) : `dry_run`, `db_url`, `bot_name`. Ajouter ces clés a changé le hash de configuration, donc l'empreinte de toute instance déjà déployée : à redéployer.

### Raisons de sortie (`ExitType`, tag 2026.9) vers F10
`roi` -> `take_profit` ; `stop_loss`, `stoploss_on_exchange` -> `stop_loss` ; `trailing_stop_loss` -> `trailing_stop` ; `exit_signal`, `custom_exit` -> `signal` ; `force_exit` -> `manual` ; `emergency_exit` -> `engine_protection` ; `liquidation` -> `liquidation` ; toute autre valeur (dont `partial_exit`, `sold_on_exchange`, vide) -> `unknown`. `force_exit` ne distingue pas un `manual`, un `flatten` ni le kill switch côté moteur : la plateforme, qui sait quelle commande elle a envoyée, affine. `position.closed` n'a pas de cause hors de l'énumération : `unknown` a été ajouté à `ExitCause` (`centrade_core/events.py`).

### Événements
Relevé par comparaison de deux lectures de l'API (le relevé fait foi) ; identifiants déterministes (UUID v5 de l'instance et de l'objet), donc un rejeu ou un worker redémarré ne crée aucun doublon. La séquence repart d'un compteur par processus, amorcé sur l'heure en secondes pour passer devant celle d'un processus précédent (un trou unique, lu comme écart par l'ingestion, déclenche une relecture). Au premier relevé d'un processus, les événements de tout l'historique sont rejoués (mêmes identifiants : l'ingestion les écarte) ; ensuite la pagination suit les clôtures, quel qu'en soit le nombre entre deux tours.

## Alternatives écartées
- Épingler `stable` ou `develop` : non reproductible (§0.14).
- Traiter l'absence d'une clé dans `show_config` comme une dérive : l'instance ne passerait jamais la vérification de F9 pour des clés que le moteur ne montre pas.
- Utiliser `freqtrade-client` tel quel : flottants, erreurs avalées, `forceenter` à portée de main.
- Redéfinir aussi `adjust_entry_price` dans la base : le moteur refuserait de charger toute stratégie.

## Conséquences
- L'adaptateur d'exécution (D2) doit : n'annuler un ordre que s'il est une entrée ; ajouter `pair_whitelist` avant `drift` ; passer le second fichier au conteneur.
- Le stop sur la venue ne se teste pas avant le live.
- Un changement de tag impose de rejouer cette vérification.
